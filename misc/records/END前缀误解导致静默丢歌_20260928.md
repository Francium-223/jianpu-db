# `%END` 用前缀匹配, 把 `%Endless_Love_…` 当成结束标记 —— 一首歌整段旋律静默消失(2026-09-28)

## 怎么发现的

导入那 1,623 份成品之后, 顺手把 `scores/` 里**没进 data.jsonl 的 498 份按原因分类**:

```
status=midi(白名单排除, 按设计)      273
无 status + 0 音符(东方曲空壳)       223
status=ocr 却没进 jsonl(★要看)        1   <- Endless_Love_无尽的爱.txt
无 status(但有 110 个音)              1   <- th075_34.txt
```

第一份就是"该进而没进" —— 而 `parse_scores.py` 的注释里写着用户当时的口径:

> 导入的 OCR 谱必须进 data.jsonl, 否则 data.json 有而 data.jsonl 没有 -> **静默丢数据**

## 根因

`score.py:to_record()` 找结束标记用的是:

```python
if s.replace(' ', '').lower().startswith('%end'):
    break
```

而**每个谱文件的第一行都是 `%<文件名>.txt` 这种注释**。于是文件名**以 `end` 开头**的谱:

```
%Endless_Love_无尽的爱.txt      <- 首行
...
'%endless_love_...'.startswith('%end')  -> True  -> 第一行就 break
```

→ `sections` 为空 → `score` 为空 → `parse_scores.py` 第 33 行 `and _r['score']` 不成立 →
**即便 `status=ocr` 也进不了 data.jsonl**。整首歌的旋律就这么没了, 而日志里只有一句
`待整理已跳过 498`, 看不出少了谁。

**影响面实测**: `scores/` 里恰好 **1 份**(`Endless_Love_无尽的爱.txt`, 46 个音)。
修完进库(69 音 / source=qupu123-313277)。

## 顺带捞回的另一首: `scores/th075_34.txt`(砕月)

它有完整旋律(216 音)、有 `MBID=aa3f0457-…`、有 `alias=碎月`、有 tagroute,
唯独**漏写了 `status=` 行** → `to_record()['status']` 是空串 → 白名单不认 → 进不了语料。

判断依据: 同批 `th075_*` 共 20 份**全都没有 status**, 其中 19 份是"有元数据、0 音符"的空壳,
**只有它真有旋律**; 而语料里带 MBID 的 36 份**全部**是 `status=ok`(手工校对那批)。
→ 补上 `status=ok`, 进库; 带 MBID 的谱 **36 -> 37**。

## 修法

```python
if re.fullmatch(r'%end\s*', s, re.I):     # 精确匹配, 不是 startswith
    break
```

## 教训

* **标记(marker)的识别必须精确**。`%END` 这种"文件级标记"和"文件名注释"共用一个 `%` 前缀,
  用 `startswith` 就会把注释当成标记 —— 这类错误的后果是**整段数据消失**而且**不报错**。
  同类隐患全库扫过一遍了:`%--` 也是 `startswith`, 但**没有任何文件名以 `--` 或 `%` 开头** ✓ 撞不上;
  `endswith('%end')` 那两处作用在"去掉换行的全文"上 ✓ 没问题。
* **"按原因分类被跳过的文件"是抓静默丢失的通用办法**: 这次是 498 份的分类,
  一眼就看出"这一份不该在这"。以后每轮重建后都值得跑一次。
* 已经做成**常驻检查**: `jianpu2/tools/qa_parse_loss.py` —— ①正文有 >=5 个音但 score 为空;
  ②status 合格、有音、却不在 data.jsonl;③没有精确 `%END`。全库实测 ① 0 / ② 0 / ③ 0。

### 附:一个操作方法上的自伤(记下来免得再犯)

想反向验证"这个新检查能不能抓到那个 bug", 我当时**把仓库里的 `score.py` 临时改回坏版本**,
跑完再在 `finally` 里还原 —— 结果那次命令**超时被 kill, `finally` 没执行**, `score.py` 就停在
坏态(靠 `git status` 才发现, 已 `git checkout -- score.py` 恢复)。

**正确做法**: 要验证"检查能不能抓到某个 bug"时, **别动仓库里的实现文件**, 而是
①改一份**副本**;或②用**已经观测到的真实数据** —— 这次就有: 那个 bug 当时实测就是
`正文 46 音 -> score 0`, 正好是新检查①的判据, 本来不需要再演一遍。
