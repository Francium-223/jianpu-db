# 注释不是属性 —— `%草原之夜1=bE2_4_中速深情地.txt`（2026-09-24）

> 用户：**"%草原之夜1=bE2_4_中速深情地.txt / 草原之夜不是attribute！！！！！！！！"**

## 0. 结论

`data.json` 里确实有一批**拿曲名当属性名**的假字段，根因是解析器把「`%` 注释」的分支放在了
「含 `=`」分支**后面**：

```python
# jianpu-db/score.py  Score.read()  —— 修之前
if '=' in i:                      # ← 先跑
    k, raw = i.split('=', 1); raws.setdefault(k.strip(' '), []).append(...)
    continue
if i == '%' + self.score.split('/')[-1]:   # ← 永远轮不到(只要这行里有 `=`)
    continue
if i.startswith('%'):
    self.comments.append(...)
```

源文件第一行几乎都是 `%<原文件名>`（写法见 `server.py` 入库那段与各抓取脚本）。只要**文件名里带 `=`**，
这一行就会被读成属性：

| 文件 | 被读成的假属性 |
|---|---|
| `草原之夜1=bE2_4_中速深情地.txt` | `草原之夜1` = `bE2_4_中速深情地.txt` |
| `有情也难牵你手1=be4_4_伤感地.txt` | `有情也难牵你手1` = `be4_4_伤感地.txt` |
| `牧羊姑娘1=F4_4_深情悠扬地.txt` | `牧羊姑娘1` = `F4_4_深情悠扬地.txt` |
| 120 首人工注释 `% 原 title=邓丽君 (爬虫把歌手名当成了曲名,已按目录名修正)` | `% 原 title` = `邓丽君 (…)` |

合计 **123 首、4 个假键**（`data.json` 的顶层键因此还长出了 `by_% 原 title` 这样的目录）。
`data.jsonl` / 前端索引 / HF 数据集**没被污染**（`to_record` 走白名单）—— 这也是为什么它一直没被
检索侧发现，只有在 `data.json`（完整元数据）里才看得见。

## 1. 修法

`score.py`：**`%` 开头的行一律先判为注释**（哪怕里面有 `=`），`%<本文件名>` 仍然只是自述、不进 comments。

```python
if i.startswith('%'):
    if i != '%' + self.score.split('/')[-1]:
        self.comments.append(i.rstrip('\n'))
    continue
if '=' in i: ...
```

## 2. 改完的核对（不是"看着对"，是逐首比）

* `data.json` 顶层键 **7820 → 7820**（集合完全一致）；
* 有变化的恰好 **123 首**，每首只**少掉**那个 `%` 开头的键：3 首文件名型 + 120 首 `% 原 title` 型；
* **同键但值变了：0 处**；残留 `%` 开头键：**0 个**；
* `data.jsonl` **逐字节一致**（`cmp` 通过）→ 前端索引/HF 两处自动跟着不变（重建 web 数据后
  `jianpu-web` 仓库 0 改动）；
* `by_%*` 假目录消失；三个 `.json` 侧车字段回到正常集合（`artist/file/source/status/tag/…`）。

## 3. 钉死它（语料门新增第 ⑧ 条）

`jianpu2/skills/jianpu-melody-lookup/selfcheck/selfcheck.py`：

```
OK  注释没被当成属性(扫到 123 处『% 开头且含 =』的注释; 假属性键 0 个)
```

两头都查：① 产物 `data.json` 里不许有 `%` 开头的字段；② 源码元数据区里每个「`%` 开头且含 `=`」的行，
它 `=` 左边那串**绝不许**出现在该曲的字段里。以后谁再把 `=` 分支挪到前面，门立刻红。

## 4. 顺带被规范化掉的 123 个曲谱文件（**注释级**，已核对）

`Score.parse()` 本来就是"读 → 规范化 → 写回"（`write_buf()` 写 `<名>_buf.txt`，再 `move_buf()` 盖回
`<名>.txt`；`check_sideeffects.py` 的用例 B 保证它**幂等**）。修好注释分支后，"规范化"的定义变了，
于是这次 `parse_scores.py` 重写了 **123 个曲谱文件**：

* 120 首：`% 原 title=…` 这类注释被**挪到文件头**（和其他注释排一起）；
* 3 首：重复的 `%<本文件名>` 自述行被去重（`write_buf` 本来就只在文件头写一次）。

逐条核对（`git diff` + 脚本）：**去掉元数据区注释后，新旧正文/字段逐字节相同**（不一致 0 个），
注释也一条没丢（只少掉那条重复的自述行）。第二次 `parse_scores.py` 后 `data.json` 的 md5 不变、
曲谱不再有新的改动 —— 说明新的规范化形式是**稳定**的；不然以后每次 refresh（读者补个链接就会跑）
都会在 123 个文件上留一堆噪声改动。
