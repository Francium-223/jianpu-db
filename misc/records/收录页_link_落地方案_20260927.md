# 收录页 `link=` 的落地方案（2026-09-27 查清 + 跑通）

## 一、先纠正一个我自己一开始的猜测：**不要**把 `source_pages.json` 灌进 `link=`

我原本以为"`link` 字段全库为空 + `source_pages.json` 有 7,132 条页面 → 直接批量写进去"。
查了前端构建才知道**这是重复劳动**：

```python
# jianpu-db.github.io/tools/build_web_data.py:192-193
"links":  [str(x) for x in (r.get("link") or [])],     # 人工补的
"srcurl": (srcpages.get(src) or {}).get("url", ""),    # 原谱站那一页(source + source_pages.json)
```

实测当前站点索引（`jianpu-db.github.io/data/songs.jsonl.gz`，7,318 条）：

| 字段 | 有值的歌 | 说明 |
|---|---|---|
| `srcurl` | **7,318 / 7,318** | 原谱站的具体页**已经全量显示**了，来源就是 `source_pages.json` |
| `links`（= `link=`） | **0 / 7,318** | 人工补的收录页，目前一条都没有 |
| `mbid` | 36 / 7,318 | MusicBrainz work 页，前端也会显示 |

所以 `link=` 的**真实用途**只剩一类：**原谱站之外的平台页**（网易云 / QQ音乐 / B站 / YouTube
的具体页面）。这些**推不出来**（要么人工找，要么调各站搜索 API），也正是它存在的理由。

> 口径（用户 2026-09-23）：「我要的不是个自动跳转到搜索页面的按钮，我要的是跳转到它
> **具体收录的那一页**」—— `jianpu-db/linkurl.py` 就是这条口径的**唯一实现**，搜索页一律拒收。

## 三、落地三步（模板已备好：`links_template_20260927.tsv`）

```bash
cd D:\Documents_D\jianpu2

# ① 先干跑, 看哪些行会被接受/拒绝 —— 必须全绿再往下
py -3.13 tools/add_link.py --from-tsv ..\jianpu-db\misc\records\links_template_20260927.tsv --dry

# ② 落盘(写进 scores/<file>.txt 的元数据区, 只动 link= 那一行, 其余字节不变)
py -3.13 tools/add_link.py --from-tsv ..\jianpu-db\misc\records\links_template_20260927.tsv

# ③ ③ 会自动重算索引(parse_scores.py + 前端 build_web_data.py), 然后:
cd ..\jianpu-db && git add -A && git commit -m "feat(link): 补收录页" && git push
cd ..\jianpu-db.github.io && git add -A && git commit -m "chore(data): 重建前端索引" && git push
#   推送后 Pages workflow 会部署, 站点上那首歌的「收录页」就多出平台入口
```

**⚠ 两个必须知道的点：**

1. **现在别跑 ②**：它会调 `parse_scores.py`，而机器上 `jp_mandopop_absorb3` 正在转写写语料
   （约 19 小时）—— 并发写就是"索引与磁盘不一致"那个老坑。要落就加 `--no-refresh` 只写曲谱，
   等流水线跑完再手动重建索引。
2. **`refresh()` 原来指错了仓库**（今天就修了）：它写死 `../jianpu-web`，而站点 2026-09-25 已搬到
   `jianpu-db.github.io`。照原样落地会**重建那份已被取代的索引**，线上一点变化都看不到。
   现在 `add_link.py` 会优先新仓库（`site_repo()`，找不到才退回旧的）。

## 四、同一个坑还有三处（今天一起修了）

前端搬家后，工具链里指向旧 `jianpu-web` 的地方：

| 文件 | 原来 | 现在 |
|---|---|---|
| `tools/add_link.py` | 写死 `../jianpu-web` | 优先 `jianpu-db.github.io`，退回 `jianpu-web` |
| `tools/check_melody_search.py` | 读 `../jianpu-web/data/stats.json` | 优先新站（交叉验证才验的是真站） |
| `tools/check_undefined.py` | 只扫 `../jianpu-web/{app,tools}/*.py` | 两边的 `app/tools` 都扫（过渡期都干净） |
| `tools/safeout.py` | 判据要求兄弟目录里**必须**有 `jianpu-web` | `jianpu-web` **或** `jianpu-db.github.io` 都认 |

最后一条最要紧：一旦清理掉旧的 `jianpu-web`，原判据会让**所有**用 `safeout` 的工具认为
"这不是真工作区"，于是把提案**写进语料库本身** —— 正是 2026-09-24 那个覆盖事故的翻版。

## 五、还缺什么（诚实版）

- **平台页的 URL 只能人来给**：本机离不了线拿到"这首歌在网易云的哪一页"。所以模板 TSV 里
  只有示例行；真正要补的是你（或将来接一个搜索 API）。
- **优先补哪些歌**：建议先补**四份榜单里已定位到的那 176 首**（用户真会搜的那些），
  再补 `todo=add tags` 的 1,099 首。名单可用 `eval_golden.py` 的输出 + `data.jsonl` 交集生成。
- **`MBID` 只有 36/7,318**：MusicBrainz 对华语覆盖本就参差，别硬凑（错配比没有更糟）。
