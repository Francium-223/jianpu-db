# qupu123 其实是**证书过期**，不是反爬 —— 以及 `source_pages.json` 的 `via` 语义审计（2026-09-25）

起因：用户丢来一个 qupu123 的页面问"你自己爬一下能找到吗"：

```
https://www.qupu123.com/tongsu/liuzi/p381073.html      →  《当那一天来临》 _通俗曲谱_中国曲谱网
```

## 一、找到根因：证书 2026-09-23 到期

之前库里一直记着"qupu123 反爬/超时（HTTP 000）"，所以这个源被当成**打不开**搁置了。
实际是：

```
$ curl -s -o /dev/null -w '%{http_code}' https://www.qupu123.com/
000                                     ← 但 curl 的退出码是 60
$ curl -sv https://www.qupu123.com/ 2>&1 | grep expire
*  Server certificate:
*  subject: CN=qupu123.com
*  expire date: Sep 23 23:59:59 2026 GMT        ← 已经过期
$ curl -sk https://www.qupu123.com/tongsu/liuzi/p381073.html
200  25202 字节  0.47s                          ← 跳过校验就正常
$ openssl s_client -connect www.qupu123.com:443 -servername www.qupu123.com </dev/null | openssl x509 -noout -dates
notBefore=Sep 24 00:00:00 2025 GMT
notAfter =Sep 23 23:59:59 2026 GMT              ← 2026-09-25 06:56 UTC 实测，过期约 31 小时
```

**curl 退出码 60 = 证书校验失败，不是网络不通。** 而 HTTP 000 只是"没拿到响应"的统称，
于是这个源被误诊成反爬，白白停了两天。

### 那张谱图确实能拿到

```
/Public/Uploads/2023/09/06/83795264f7f4bd6394b.png
  → 200, image/png, 1.58 MB, 2480 x 3508 (A4@300dpi)
  → md5 8696b47d1a2aec8582a5ad29bdc0e65c
  → 本地留证: _analysis/evidence/qupu123_p381073_当那一天来临.png
```

这也是 `crawl_qupu123.py` 文档里说的"最清晰的源"的分辨率，确实到手了。

### 但它**同时**还有限流

用 `-k` 拿到前 3 个响应（页面、证书、图片）之后，该 host 开始**在 TLS 握手上超时**
（45s），且跟校不校验无关：

| 方式 | 第 1 次 | 之后 |
|---|---|---|
| curl -k 页面 | 200 | 连续 3 次 000 / 45s 超时 |
| python 校验证书 | 握手超时 20s | 握手超时 |
| python 不校验证书 | 握手超时 20s | 握手超时 |

所以结论是**两件事叠加**：证书过期（真问题，已修）+ 少量请求后被限流/掐连接（真存在）。
爬它必须慢速 + 重试，不能并发猛打。

## 三、修了什么

**新增 `jianpu2/tools/tlsfetch.py`** —— 取页时对过期证书的兜底，口径：

1. 先用**正常校验**取；
2. 只有真的抛"证书过期/校验失败"时，才对**这一个 host** 改成不校验重试一次，并在 stderr 打一行警告（每 host 一次）；
3. 超时 / 拒绝 / 404 照旧抛出 —— 免得把"站真挂了"误判成"证书问题"。

离线自检（`python3 tools/tlsfetch.py`）覆盖了这三条分流：证书错误 → 兜底；超时/拒绝/404 → 不兜底。

**接线两处**：

* `tools/verify_source_urls.py::fetch` —— 原来那句兜底是**死的**：
  ```python
  def _ssl_ctx():
      try:    return ssl.create_default_context()
      except: return ssl._create_unverified_context()      # ← create_default_context 根本不抛
  ```
  证书过期是在**握手**里才炸的，`except` 永远走不到 → 所有请求被记成 status 0。
* `tools/crawl_qupu123.py::get` —— 原本是裸 `urlopen`，同样必然失败。

`check_tools.sh` 加了 tlsfetch 的自检块。接线后对健康站点实测：`--sites jianpujia --limit 3 --recheck`
→ **3/3 核对成功**（说明没改坏）；`--sites qupu123 --limit 2`（workers=1, interval=8s）
→ 0/2，全是 miss（印证上面"还在限流"）。

## 四、顺手审计出 `source_pages.json` 的 `via` 语义问题（**没动数据**）

7,132 条的 `via` 分布：`title` 7,008 / `id` 124。看着像"只有 124 条证据可靠"，
但 `check()` 是**先查标题、标题不过才查 id**，所以 `via` 记的是"哪个先过"，不是"最强证据"。
真正的差别在于 URL 是**怎么来的**：

| 站 | 候选 URL 怎么来 | 路径里有 id 算不算证据 |
|---|---|---|
| jianpucn | `candidates()` **按 id 拼**：`/pu/{sid[:2]}/{sid}.htm` | ❌ **循环论证** |
| jianpujia | `candidates()` **按 id 拼**：`/{section}/{sid}.html` | ❌ **循环论证** |
| qupu123 | `find_qupu123()` **站内搜索**搜出来的 | ✅ 真证据 |

所以：

* `via:title`（7,008 条）= 标题命中，**是独立证据**，跟站点无关；
* `via:id` 里 **qupu123 的 24 条** = 真证据；
* `via:id` 里 **jianpucn 64 + jianpujia 36 = 100 条** = **没有独立证据**：
  只证明了"我们自己按 id 拼出来的 URL 返回了 200"（而标题没对上）。

**没有改 `source_pages.json`**（它是 `verify_source_urls.py` 的产物，且该脚本只写"核对成功"的条目，
盲跑会把核对失败的条目直接丢掉）。要做的话得：先跑/写到独立文件 → 与现表 diff → 再决定，
并且给这三个站的 id 证据分开命名（如 `via: "constructed"`）。已记进待办。
