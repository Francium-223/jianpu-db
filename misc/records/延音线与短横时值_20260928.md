# 延音线、短横时值、以及"第三份口径" —— 2026-09-28 夜

这一轮是从"`score` 里有 192 个**有符号没音高**的碎片,是不是丢音高了?"这个问题开始的。
结论分三块,每一块都改了东西,所以留档。

---

## ① `c~` / `q~` / `s~` 是**延音线**,不是丢音高(191 个)

原来的说法(**错的**,已经写进了 `tools/count_note_fragments.py` 的 docstring,现在改掉了):
> `c~` = 时值字母 + 连音线, **没有音高** —— 放在一串音高之间很可能是**那里丢了一个音高的音**。

四方印证它是 jianpu-ly 的 tie:

| 证据 | 看到的东西 |
|---|---|
| ① jianpu-ly 源码 | 第 137 行:`Ties (like Lilypond's, if you don't want dashes): 1 ~ 1`;第 1776 行注释 `# tie from the number, not the last dash` |
| ② `train-data-seq/manifest.jsonl` 的压缩形 | 同一处写作 `0c 0 6 7 '1 - - - ~ '1q '1q '2 '3 …` —— 波浪号在短横后面 |
| ③ 生成的 `.ly` | `\=JianpuTie( ~ \once \override Tie… \note-mod "–" c''4 …`,即一条 tie 跨过整小节 |
| ④ 渲染出的 PNG | `th01_05.png` 第 2 小节 `1 - - -`,连音弧拉到第 3 小节的第一个 `1` 上 |

顺手算了一遍 `th01_05` 的 verse,和 PNG 上的分小节**完全吻合**:

```
c0 c0 c6 c7            = 4 拍        -> PNG 第 1 小节 "0 0 6 7"
c'1 c- c- c-           = 4 拍        -> PNG 第 2 小节 "1 - - -"
c~ q'1 q'1 q'2 q'3 q'2 q'1 q7 q5 = 0 + 8×0.5 = 4 拍 -> PNG 第 3 小节 "1 1 2 3 2 1 7 5"
```

`c~` 走 `recover_bars` 里"根本不是 token"那条分支 -> **0 拍 0 音高**,正是延音线该有的样子。
没有音高、不占拍、前端逐 token 原样渲染成 `c~` —— 三处都不需要改。

`1=C`(**1 个**,`qd1z_anthem.txt` 的 intro)是**调号**:语料没有调号字段,前端又是逐 token
原样渲染,写在正文里正好把调号显示出来。同样 0 拍 0 音高。

**改动**:`tools/check_corpus_invariants.py` 把这两类从"报警"降级为"良性记号,只报数"——
一个永远红的检查等于没有检查,报警要留给真问题。`tools/count_note_fragments.py` 的 docstring 更正。

## ② 带字母的短横,**时值要看字母**(全库 35 个,6 首受影响)

`recover_bars` 里原来这一行:

```python
if t == "-" or re.match(r"^[cqsdh]+-$", t or ""):
    acc += 1.0      # ← 写死 1.0, 不看字母
```

`q-` 是 **半拍**(八分),却被当成一整拍 —— 该小节之后的线全部偏移。
证据仍然是参考实现,而且这次是**逐例对上**的:

* jianpu-ly 把 `q-` 渲染成 `\note-mod "–" c''8`(八分 = 0.5 拍);
* `tools/check_beats_vs_lilypond.py` 在 4 首带 `.ly` 的谱里比 2160 个事件,
  **只有 10 处不一致,全部是"音级 `-`,jptok=1.0 / .ly=0.5"**,数量正好等于各谱的 `q-` 个数:

| 谱 | `q-` 个数 | 比对里报的分歧 |
|---|---|---|
| th01_03 | 5 | 5 |
| th02_05 | 4 | 4 |
| th02_01 | 1 | 1 |
| th17_13 | 12 | (无 .ly) |
| th10_06 | 8 | (无 .ly) |
| th07_13 | 5 | (无 .ly) |

**改动**:`acc += beat(t)` —— 不需要特例了(`beat("-")`=1.0、`beat("q-")`=0.5 本来就对)。
`jianpu-db/score.py` 的内置兜底同样改(它有 parity 测试锁着,不同步就会红)。

### 一个被我推翻的中间结论(方法上的教训)

第一次比较用的是"**线位**":`tools/check_bars_vs_lilypond.py` 报"731 个线位只对 180 个 = 24.62%",
看起来像"拍值模型整个错了"。**那个数字是假的**,两个原因:

1. 语料 `score` 是**展开形**(`q'1 q6 q3 …` 每个音都带字母),而 `manifest.jsonl` 的 `text` 是
   **压缩形**(`'1q 6 3 …` 只有首个带字母)。`.ly` 是从哪份渲染的会整体影响线位。
2. 首次命中可能落在**小节中间**,相对线位就整体平移了。

改成**逐事件比时值**(与落在小节哪里无关)之后:2160 个事件 **99.54% 一致**,唯一分歧就是上面那 10 个 `q-`。
教训:拿"位置"当判据时,要先排除输入差异与相位;能比"局部量"(每个音的时值)就别比"全局量"(第几条线)。

## ③ `jptok` 的**第三份**实现:前端 `static/jptok.js`(以前没人管)

同一个口径现在有三份:

| # | 位置 | 谁锁着 |
|---|---|---|
| ① | `jianpu2/skills/jianpu-melody-lookup/jptok.py` | **唯一真源** |
| ② | `jianpu-db/score.py` 的 `_FallbackJptok` | `jianpu2/tools/check_jptok_parity.py`(7816 份谱 / 723 万 token 逐项比) |
| ③ | `jianpu-db.github.io/static/jptok.js` | **以前没有** —— 于是它真的漂了 |

实测 ③ 的 `BEAT` 表写着 `h: 2.0`(二分音符),而 Python 侧 2026-09-24 已定案 **h = 六十四分音符 = 0.0625**
(证据见 `jptok.py` 里那段说明:项目自己的 jianpu-ly 写着 `types={"64th":"h", …}`)。
`jptok.js` 自己的文件头还写着"改这里时必须同时改 Python 侧"。

**改动**:

* `static/jptok.js` 的 `BEAT` 表改成 `h: 0.0625`;
* 新增 `jianpu2/tools/dump_jptok_tokens.py`(导出全语料每个**不同** token 的判定:21709 个)
  与 `jianpu-db.github.io/tools/check_jptok_js.mjs`(在 JS 侧逐个重比),
  再用 `tools/check_jptok_parity.sh` 串成一条命令,已挂进 `tools/check_all.sh`
  (`JIANPU_QUICK=1` 跳过)。

**这道锁不是恒真的**(故意验过):把 `h` 改回 `2.0`,检查立刻报 **799 处不一致**,例:
`"h#1" is_pitch py=1 js=1 | beat py=0.0625 js=2`;还原后 exit 0。

> 注:`beat()` 在站点里**没有任何 import**(前端只用索引里算好的 `bars`),所以这次漂移
> 对线上功能没有实际影响 —— 但"一份没人管的口径"本身就是下一个事故的种子,所以照锁不误。

## ④ 同一个根因的**第二次**事故:CI 把我的去重改了回来

推完"去掉重复小节线"之后,`jianpu-db` 的推送被拒(非快进)—— 远端多了一条
`c1063916 chore: auto-regenerate folder [skip ci]`,它改了 `data.jsonl`:**3044 行增 / 3044 行删**。

原因就写在 `.github/workflows/parse.yaml` 自己的注释里:runner 只 checkout 本仓库,
而 `jptok.py` 住在**兄弟仓库** `jianpu2/skills/jianpu-melody-lookup`;`actions/checkout` 的 `path`
又不能越出 workspace,所以兄弟仓库落在 `<repo>/jianpu2`,而 `score.py` 找的是 `<repo>/../jianpu2`
—— **CI 一直走的是 `score.py` 里的内置兜底**。那一刻兜底还没同步"去重",
于是 CI 忠实地把**带重复小节线的** `data.jsonl` 又生成出来并提交。

结果:远端语料 **3044 首**有重复线(`101.txt [3, 6, 7, 7, 8, 8]` 正是当初那个例子),
而我发布给前端的索引(来自本地那份)是干净的 —— 两边不一致。

两个口径本来有 `jianpu2/tools/check_jptok_parity.py` 锁着,但**那道锁不在 CI 里跑**,漂了没人喊。
这次补上:

* `tools/check_data_sane.py`(**自包含、不依赖 jianpu2**):断言 `bars` 严格递增、不越界、
  `sections` 拼起来 == `score`、`file` 存在且不重复、行数下限;
* `parse.yaml`:重建完**先断言再提交**(口径漂了就让 workflow 红,而不是静默改写 3000 首),
  并且兄弟仓库在场时**直接再跑一遍 parity**(723 万 token 逐项比)。

反向验证:拿 CI 那份坏数据跑新断言,正好报 `bars 有重复/非递增 3044`。

> 教训:凡是"两个实现必须一致"的约定,只在**有人跑**的时候才成立。
> 本地跑绿 ≠ 流水线跑绿 —— 断言要放进那条**真正会写数据**的流水线里,并且放在写之前。

## ⑤ 顺带挖出的第三处:前端产物的哈希名字**平台相关**

给站点补 `static/jptok.js` 的修正时,发现 `jianpu-db.github.io` 的推送被拒 —— 远端多了一条
`3549560 chore(pages): 同步构建产物到仓库根 [skip ci]`,把 `jptok.748e2c28.js` 改成了
**`jptok.49138bb1.js`**。而我本地按同一份源码算出的是 `12ec86b0`。**同一份文件两个名字**。

原因:本机 `core.autocrlf=true`,工作区是 **CRLF**(4,598 字节),而 git blob 是 **LF**(4,510 字节)。
`build_dist.mjs` 拿 `readFileSync(src)` **原始字节**算 sha256 —— 于是:

```
sha256(LF blob)     = 49138bb1   <- 流水线(Linux)算出来的, 也是仓库里那个名字
sha256(CRLF 工作区) = 12ec86b0   <- 我在 Windows 上算出来的
```

也就是说 `.github/workflows/pages.yml` 那条"构建 → 同步产物到仓库根 → 提交"每次都会
**把四个文件全部改名**,而我在本地同步一次又会改回去 —— 两边来回抖。
(我一开始还误判成"仓库里那批名字来路不明、跟内容哈希对不上",因为我是拿 CRLF 去比的;
`search.js`/`style.css` 没改过却"名字不同"正是这个原因。记在这里免得下次又绕一圈。)

`build_dist.mjs` 里还有一处**真的**不是内容寻址:原来的名字是拿**源文件**算的,而写出去的
`app.<hash>.js` 里 import 的是 **jptok 的新名字** —— 于是"只改了 jptok、没动 app"的提交会让
**app 的名字不变而内容变**。Cloudflare 给 `/static/*` 设的是 `max-age=31536000, immutable`,
那块客户端会一直发旧的 `app.<同名>.js`,而它 import 的旧 jptok 已经随部署删掉
-> import 404 白屏,刷新也没用。

**改动**(都在 `jianpu-db.github.io/tools/build_dist.mjs`):

* 按**依赖顺序**处理(jptok → search → style → app),先把引用改写成新名字,**再对最终内容取哈希**;
* 读入即 `\r\n` → `\n`,产物也按 LF 写出 —— 于是"同一份源码 = 同一串字节 = 同一个名字"。

**验证**:

* 四个产物的名字 == sha256(自己内容) 前 8 位,且产物里 CRLF = 0;
* 本地算出的名字与流水线给出的**完全一致**(`jptok.49138bb1` / `search.b5641f8f` / `style.c37e47bd`);
* 连建两次名字相同(确定性);
* 临时给 `jptok.js` 加一行注释:`jptok.49138bb1 -> 11a6a67d` 且 **`app.25e0ed03 -> f523b844`**
  —— 引用者的名字确实会传播(旧规则下 app 不变)。

线上复核(改完 push 之后,`pages.yml` 自己同步 + 发布):

```
线上 stats      songs=7318 with_images=7277 image_pages=9069 image_sources=17167
线上 songs.jsonl.gz  7318 首, 重复/非递增 bars = 0
线上 q- 那 4 首      bars 与语料逐条一致
线上 jptok 产物      const BEAT = { h: 0.0625, ... }
线上 app 产物        import ... from './search.b5641f8f.js' / './jptok.49138bb1.js' (都在)
旧产物 app.cab288ac.js / jptok.748e2c28.js -> 404
```

CI 状态:`Parse Scores Metadata`(带新断言与 parity 步骤)**success**、`Publish to HuggingFace`
**success**、站点 `Deploy to GitHub Pages` **success**。
(HF 那份没法在本机复核 —— 本机到 huggingface.co 的线路是被污染的,workflow 头里写着。)
