# 前后端检索等价性（2026-09-24 07:35–07:55）

> **报告的指标出自 Python 侧**（`lookup.py` / `eval_golden.py`），**用户实际在浏览器里跑的是**
> `jianpu-web/static/search.js` —— 同一套代价模型的**两份实现**（和 jptok 那两份一个道理）。
> 这一节回答一个问题：**榜单上那个 98.3%，用户在网页上真能得到吗？**

## 做法（一条命令）

```bash
bash jianpu-web/tools/check_parity.sh [榜单.tsv]     # 默认酷狗华流
```

1. `eval_golden.py --dump-queries`（**新加的参数**）：把 Python 侧**真的用过的查询片段**
   （L=15、错音 0、per-song=1）连同"这题期望命中哪首"导出成 TSV；
2. `check_js_parity.mjs`：把同一批片段喂给 `static/search.js` 的 `search()`，
   逐条比对 **Top-1 曲名组**是否与 Python 侧的期望一致，并报 Top-3/Top-5 是否含期望。

## 四个榜单的结果（都是 L=15 / 错音 0）

| 榜单 | Python 侧报的 Top-1 | JS 侧重放（Top-1 同名） | JS 侧 Top-3 / Top-5 含期望 |
|---|---|---|---|
| cma 30年30歌 | 100.0% | **28/28 = 100.0%** | 100% / 100% |
| 华语流行百佳 | 98.9% | **85/87 = 97.7%** | **100% / 100%** |
| 酷狗华流 2025 | 98.3% | **59/60 = 98.3%** | **100% / 100%** |
| TME 2024 十大 | 100.0% | **1/1 = 100.0%** | 100% / 100% |

**结论：前端与后端等价** —— JS 侧逐条复现了榜单的 Top-1，Top-3/Top-5 一律 100%。
也就是说 `_analysis/eval_*.txt` 里那些数字，就是用户在 `http://127.0.0.1:8770/` 上得到的东西。

## 那 2 条"不一致"是什么

cn_pop 少算 1 条、酷狗少算 1 条，都是同一类：
期望值取的是**查询源谱**的曲名组（例如合唱版 `无名的人二部合唱`），而两侧都把
`无名的人`（同一首歌的另一个版本）以**代价 0** 排在 Top-1。
Python 侧的命中判定用的是"包含"口径（`same()`：被包含方 >=4 字且占长串一半以上），
严格按这个规则这两题**在 Python 侧也不算命中**；我的 JS 比对用的是**组名完全相同**，
所以显示成"不一致"，其实两边**判定结果一致**（都算未命中 / 都找到了同一个替代版本）。
脚本里已经把这层说明打出来了，免得以后误读。

## 现状

* 这是一个**可重复的检查**（`check_parity.sh`），以后改 JS 或改 Python 检索都可以跑一遍；

  所以用**等价性测试**兜住，做法与 `check_jptok_parity.py` 一致。
