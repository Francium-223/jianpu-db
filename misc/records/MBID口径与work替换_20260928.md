# MBID 的口径是 work —— 以及"为什么只有 36 条"的答案(2026-09-28)

`propose_mbid.py` 卡在一个决策上:"高置信度清一色是 `recording`,而库里的约定看起来是 `work`"。
这轮把它查成了事实,并且修好了。

---

## ① 库里的约定:**work**(36/36 实测)

拿语料里**全部 36 条** MBID 去问 MusicBrainz(每条一次 `GET /ws/2/work/<id>`):

```
th01_01  work 200  A Sacred Lot            recording 404
th01_02  work 200  永遠の巫女                recording 404
th01_03  work 200  The Positive and Negative  recording 404
th01_04  work 200  Highly Responsive to Prayers  recording 404
th01_05  work 200  東方怪奇談                recording 404
th10_06  work 200  神々が恋した幻想郷          recording 404
th15_13  work 200  ピュアヒューリーズ 〜 心の在処  recording 404
… 34 条直接 200, 另 2 条首次 503(限流)重试后也 200 -> **36 / 36 全是 work**
```

前端的 MusicBrainz 链接也写死 `/work/<mbid>`(`make_link()`)。**约定是 work**,没有疑问。

## ② 为什么"高置信度全是 recording"—— 是结构, 不是排序错

`musicbrainz_lookup()` **本来就同时查 work 与 recording**,排序键第 305 行就是
`(置信度, work 优先, score 降序)` —— 同分时 work 已经优先。问题出在**评级**:

* MusicBrainz 的 **work 实体通常不带 artist**(works 挂的是作曲者, 搜索接口返回的 `artists` 常为空)
  → `artist_ok()` 对 work 永远不成立 → work 最高只能评到 `medium`;
* recording 有 `artist-credit` → 能评到 `high`。

所以"high 全是 recording"是这个数据结构的必然结果 —— 照它写库会生成 `/work/<recording-id>` 的**死链**。

## ③ 改法:命中 recording 就**顺着 work 关系换成 work 的 id**

新增 `convert.musicbrainz_recording_work(rec_id, want_title)` + 在 `musicbrainz_lookup` 的出口处:

* 命中 `recording` → 查 `GET /ws/2/recording/<id>?inc=work-rels`;
  * 恰好一个 work → **换成那个 work 的 id**(`kind="work"`), **置信度不变**
    (证据仍是那条 recording 的标题+歌手, 记在 `matched.via` / `matched.work_title`);
  * 多个 work → 挑标题完全一致的那个;
  * 一个都没有 → **照原样返回 recording**(不丢信息), 由调用方决定收不收 —— 但**不要写**。
* 顺手在 `propose_mbid.py` 的结尾把 `(实体类型, 置信度)` 分列打印, 并明说
  "**只有 kind=work 能落地**"。

## ④ 实测:只有约 21% 的 recording 能换成 work

先抽样(12 条 high recording → 2 条有 work, ≈17%), 再全量换
(`tools/upgrade_mbid_cache_to_work.py`, 1.3s/次, 备份缓存后再改):

```
待换 427 条 -> 换成 work 90 / 没有 work 337 / 出错 0     (21.1%)
换完之后缓存的 (置信度, 实体类型) 分布:
   ('(空)', '(空)')           568     <- 查了但没命中
   ('medium', 'recording')  171     ┐ 拿不到 work 实体
   ('high',   'recording')  171     ┘ -> **不要写**
   ('medium', 'work')       131     ┐ 可以写(medium 按口径要复核)
   ('high',   'work')        34     ┘ 可以写
```

**能落地的是 165 条(34 high + 131 medium)**;另有 342 条 recording 拿不到 work,不写。
抽查换来的 work id:5 条全部 `GET /work/<id>` 200 且标题与缓存一致 ✓
(`Always Online` / `一半` / `一水隔天涯` / `一荤一素` / `一起摇摆`)。

**没有应用**(不写语料):落地要往 `scores/*.txt` 写 `MBID=`(`convert.py` 的"只补 MBID 模式",
已带 MBID 的会跳过), 按项目口径"错配比没有更糟", 这一步等人拍板。命令:

```
py -3.13 convert.py --mbid-only --artist-map <...>        # 见 convert.py 1109 行起的说明
python3 tools/verify_mbid_proposal.py --cache <缓存快照>   # 落盘前独立反查实体
```

## ⑤ 顺带解开的旧谜:**scores/ 里 517 份有 `MBID=`,而 data.jsonl 只有 36 条**

`tools/_mbid_audit.py` 的疑问("1034 份带 MBID, 为什么只有 35 条进 data.jsonl")现在有确切答案:

```
scores/ 7816 份; 带 MBID= 的 517 份, 按 status 分布:
   (无 status) 208   <- 东方曲的元数据空壳(0 音符)
   midi        273   <- MIDI 硬转, 白名单按设计排除
   ok           36   <- **恰好全部进了 data.jsonl**
data.jsonl 里 MBID 非空: 36
★ "谱里有 MBID 且进了 data.jsonl, 但 jsonl 里 MBID 为空" 的**真丢案例: 0 条**
```

不是丢, 是白名单按设计把那 481 份挡在外面(`status=midi` 会毁掉检索, 见自检门第 ⑦ 条)。
