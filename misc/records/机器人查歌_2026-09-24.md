## 1. 先说发现的毛病：melody_search.py 原来永远查不到东西

它搜的是 `batch-out/*.txt` —— 旧流水线的中间产物，**8,495 个文件里没有 th10_06**：

```
$ python3 tools/melody_search.py 33565653253
查询数字串: 33565653253  (11 个音)
命中 0 首          ← 而这首确实存在（前端查得到）
```

它不报错，只是永远空手而归（和 `batch-out` 一样名的旧目录还有 4 个）。所以"接上机器人"之前
必须先把**语料来源**换掉，否则这个功能是假的。

## 2. melody_search.py 的大修

| 项 | 之前 | 现在 |
|---|---|---|
| 语料 | `batch-out/*.txt`（旧中间产物, 没有 th10_06） | **`jianpu-db/data.jsonl`**（唯一真源, 7321 首, status ∈ {ok,ocr}） |
| 切 token | 自写正则 `^[,']*[qsdh]*[,']*([1-7])` —— 静默丢掉 `b7`(降号) 与 `6c.`(后缀时值) | **`jptok.py`**（全库唯一 token 实现）—— 与 2026-09-23"索引丢音"事故同一类坑 |
| 回话数据 | 只有文件名 | 曲名/歌手/出处/记谱文件/音符数/状态/命中位置/差几处 |
| 多段 | 无 | `63731232 1765` —— 每段都要出现在同一首里 |
| 容错 | 每窗口把整段加完再判断（长查询慢到不可用） | 边比边数、超了就跳（`--fuzzy 1` 可用） |
| 输出 | 只有人读的文本 | 人读文本 + `--json`（机器人读这个） |
| 速度 | — | 冷启 6.1s（读 13MB jsonl + jptok 切 130 万 token）；**缓存后 0.10s** |

**音数交叉验证**：melody_search 解出 **1,301,430** 个音，与前端索引 `stats.json` 的 `notes`
**一模一样** —— 两条独立链路（Python 检索 vs web 构建）用同一个 jptok，数字对得上。

缓存：`~/.cache/jianpu/melody_index.json`（2.8MB），指纹 = `data.jsonl` 的 size + mtime_ns + `TOKVER`。
语料一变就重建（不做"看着像"的过期缓存），`--no-cache` 可绕过。**不往任何仓库里写东西。**

## 3. 插件 `awesome_bot/plugins/melody.py`

* 触发：`on_endswith("是什么歌")` —— 与诗词插件的 `on_endswith("是什么诗")` 同一套路，互不抢；
* 不足 5 个音不查（与前端同一条规矩），只认 1-7；
* 严格匹配为空 → 自动退一步 `--fuzzy 1`，并把"差 N 处"写在结果里；
* 回话最多 6 条、超长截断（QQ 消息别爆）；脚本缺失/超时/异常都给一句人话；
* 全可配：`JIANPU_MELODY_SEARCH` / `JIANPU_PY` / `JIANPU_DB` / `JIANPU_MELODY_TOP` / `JIANPU_MELODY_TIMEOUT`。

**自检抓到的一个真 bug**：第一版把 `smg.finish(...)` 包在 `try/except Exception` 里 ——
而 NoneBot 的 `finish()` 是靠抛 `FinishedException` 结束处理器的，它**是 `Exception` 的子类**，
于是每条成功回话后面都会被再补一条"查歌出错了："（`check_melody.py` 里那条断言就是钉它的）。
修法：`try` 只包住真正会出错的 `run()`，`finish()` 全在 try 外面。

## 6. 边界

* 排序是 **不同数 → 谱短 → 曲名**（短谱里出现一段长旋律更可能"就是它"）。
  **没有按热度破并列** —— 前端那套"同曲名组越多越热"的 tie-break 没搬过来；
  像 `11111111` 这种常见数字串会命中好几首，只列前 6。
* melody_search 只管**音高数字**（不比变音记号/八度），与前端检索的代价模型不是一回事：
  前端会区分 `#4` 与 `4`，这里不区分（用户口径就是"输入数字返回结果"）。
* 语料更新后第一次查询会重建缓存（约 6 秒），之后 0.1 秒。
