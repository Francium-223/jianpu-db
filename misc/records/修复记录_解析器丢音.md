## 3. 顺带发现的两件小事

1. **行尾收敛（好事）**：git 里存的是 **LF**，而这块 Windows 工作区是 **CRLF**（autocrlf 所致）。
   在 Linux 上重生成后 `scores/*.txt` 全部变回 LF，与提交内容一致 ——
   `jianpu-db` 的 git 脏条目从 **60,475 降到 15,837**（剩下的是 `by_*` 符号链接与生成物）。
2. **`1=C` 调号**：全库 1.6M 个 token 里唯一"不是音符也不是延长记号"的东西（只出现 1 次，
   在 `qd1z_anthem.txt`）。它现在被**显式保留**在 `score` 里，因为那是 `data.jsonl` 里唯一残留的调性信息。

## 5. 第二轮（同一天更晚）：两个「休止」引发的 bug

用户打开本地部署的页面，一眼看出两件事：**标黑的是 `c0 q0 q3 q3` 而不是 `q3 q3`**、**小节划分看着不对**。
两条都成立，而且是同一个病根：**休止被当成"不算数"**。

### 5.1 前端：休止被算成"音符"，高亮与小节线整体前移

`jianpu-web/static/app.js:renderScore` 用 `parseToken(toks[i])` 数「第几个音符」，
而 `parseToken` 对休止 `c0`/`q0`、念白 `x` **也返回非空**；索引里的 `at`/`bars`/`n` 只数**有音高**的音
→ th10_06 开头两个休止，把标记整体推前 2 个 token：标黑从 `c0` 开始、第一条 `|` 画到 `q3 q3` 之后。

**修**：`jptok.js` 新增 `isPitch()`（与 Python 侧 `is_pitch` 同口径），`renderScore` 改用它；
`renderScore` 顺带 `export` 出来，好让自检能直接验它。

### 5.2 后端：休止不计拍，小节线整体前漂

`jptok.recover_bars` 里原来写着：

```python
if not p or p[0] is None:
    continue                      # 休止/念白: 保守不计时
```

于是"小节 = 4 拍旋律"而不是"4 拍时间"—— **只要谱里有休止，小节线就整体提前**。
th10_06 开头有 2.5 拍休止，所以第一条线早了 1.5 拍。

**修**：休止/念白照样 `acc += beat(t)`，只有"有音高"的音才推进"第几个音符"。修好后：

```
小节 1: c0 q0 q3 q3 q5        ← 2.5 拍休止 + 三个八分音符弱起 = 正好 4 拍
小节 2: c6. s5 s6 q5 q3 q2 q5 ← 正好 4 拍
小节 3: c3 q3 q5              ← 正好 4 拍
```

### 5.3 数字（实测）

| 指标 | 修前 | 修后 |
|---|---|---|
| **旋律**（音高串）变化的曲数 | — | **0 / 7385**（只动小节线，不动音） |
| 小节数发生变化的曲数 | — | 6,498 / 7385（**全部变多**：以前把休止的时间从总时长里扣掉了） |
| th10_06 小节数 / 前 8 小节真实拍数 | 66 / 前几小节 5.5、4.5… | **68 / 4.0 4.0 4.0 4.0 4.0 4.0 4.0 4.0** |
| 非末尾小节"正好等于拍号"的比例（有显式拍号的谱） | 44.5% | **49.7%（+5.2 个百分点）** |
| 高亮是否含休止 | 含（`c0 q0 …`） | **不含**（`q3 q3 q5 c6. s5 s6 q5 q3 q2 q5 c3`，与查询逐字相同） |

> 剩下约一半小节仍然不"正好等于拍号"：主要是**长音跨小节**时的取整（累加到 ≥ 拍号才落线，
> 会过冲）以及 OCR 时值本身不精确 —— 不是这次修复的目标，也不影响检索
> （检索只看音高与升降号）。

### 5.4 自检门增加到 5 条（并做了反向验证）

新增用例⑤：**th10_06 第一条小节线必须在第 3 个音符之前**。
拿"休止不算拍"那一版旧数据跑同一个门 → **被拦住**；跑当前数据 → 通过 ✓。
前端也补了回归测试：`node jianpu-web/tools/check_page.mjs 33565653253`
会断言"标黑段里没有休止/念白、且标黑的音 == 查询"。

## 8. git 事故与救援（2026-09-24 00:2x）

**用户看到的现象**：`jianpu-db` 工作区突然"干净"了（改动全没了）、`git status` 显示**落后远端 1 个提交**、
命令行里一堆不认识的英文 —— "我不会搞了"。

**三件事叠在一起**：

1. **`git stash`**：有人（或 Git 图形工具）执行了 stash —— 改动被**收进抽屉**，不是删除。
   `git stash list` 能看到：`stash@{0}` = 本次全部改动（1737 文件），`stash@{1}`/`{2}` = 更早的 WIP。
2. **`git fetch`**：远端多了一个提交 `bbfd02b5 chore: auto-regenerate folder [skip ci]`
   —— 是**打包当天 GitHub Actions 自动提交的**（只把 `by_copyright/` 里 55 个目录名改成正确大小写，
   0 增 0 删）。本地因此"落后 1"。
3. **`core.ignorecase = true`**（Windows 留下的配置，跑到 Linux 上）：文件系统区分大小写，
   于是 `Dekyo Ongen` 与 `Dekyo ongen` **两个目录同时存在**（源数据里同一贡献者确实有两种拼写），
   而 git 以为它们是同一个路径 —— 状态报告、暂存、重命名全部错乱（实测有 **10 组**仅大小写不同的目录）。

**救援步骤（都做完了）**：


**教训**：
- `git status` 干净 **≠** 改动没了 —— 先 `git stash list` 看看。
- 永远别用"丢弃所有改动"（discard）—— 那个才是真删；`stash` 是可恢复的。
- 跨 Windows/Linux 的仓库，`core.ignorecase` 必须按当前系统设对，否则大小写不同的路径会互相打架。
