## 2. 抓到的 5 个坑（都是"静默"型 —— 用户以为投上了，其实没有）

| # | 现象（实测返回） | 根因 | 修法 |
|---|---|---|---|
| 1 | `{"score":"63731232 1765"}` → `score_file:""`，提示"只留了投稿，没有数字" | 归一化只在「整串**没有空格**」时才拆数字；用户手打了空格 → 整串被当非法 token 全丢 | 抽出 `normalize_melody()`：无论有没有空格都按「数字/时值后缀/八度撇 + 下一个数字或记号」补空格 |
| 2 | `committed:false` + `error: 路径规格 'scores/xxx.txt' 未匹配任何 Git 已知文件` | `git commit -- <path>` **不含未跟踪的新文件**（原来的 `git add -A feedback scores` 顺便在替它 add） | 新增 `_git_commit()`：先 `git add -- <本次文件>`，再限定路径提交 |
| 3 | `{"tags":["民歌"]}` → `500 TypeError: expected string or bytes-like object, got 'list'` | `re.split` 直接吃 `payload["tags"]` | 统一 `_as_text()`（list/tuple/None/int 都能收） |
| 4 | 同一秒内同曲名投两次 → 两份留档**同名互相覆盖** | 留档 id = 时间戳+曲名 | `_unique_rid()`：撞了就 `-2/-3…` |
| 5 | `{"score":"abc 你好 12345"}` → 建出 5 音谱，**不告诉用户丢了东西** | 认不出的字符被静默丢弃 | 返回 `score_warn`，前端在成功提示里带出（"有 N 个字符没认出来丢掉了：…"） |

配套：`fix`/`meta` 现在自动带上「刚才查询命中的那一份」（前端 `LASTFILE` → 留档 `target` 字段 +
新谱里写 `% 纠错目标 <file>`），作者不用猜说的是哪首。

## 3. 顺手排掉的两个更危险的隐患

### 3.1 并发投稿会丢提交（git index 不是并发安全的）

同一秒 3 连发（`curl ... &`）实测：3 份留档都写下了，但只有 1 份 `committed:true`，另两份报
`路径规格…未匹配`。修：`GIT_LOCK`（进程内串行）+ 命中 `index.lock` 时等 1.5 秒重试一次；
并且**提交失败的原因现在会显示给用户**（以前前端只写"（未提交）"）。

### 3.2 `jptok.py` 找不到时会"静默换一套口径"（这条最要命）

`score.py` 原来 `except Exception: 用内置兜底`，只 `warnings.warn`。兜底是**第二份实现**，
两份一起漂过一次（36 首受损，见 `修复记录_解析器丢音.md`）。静默降级意味着
**整个 data.jsonl 可能按另一套 token 规则重建，而没人发现**。

修：`jptok` 变硬依赖 —— 找不到直接报错退出（与 `export_hf.py` 同态度），并提示
`JIANPU_JTOK=<skill 目录绝对路径>`；确实要在没有 jianpu2 的环境跑，显式设
`JIANPU_ALLOW_FALLBACK_JTOK=1`。真机不受影响（相对路径找得到，实测打印
`.../jianpu2/skills/jianpu-melody-lookup/jptok.py`）。

## 4. ⚠️ 我自己造成的污染事故（已复原，如实记录）

**发生了什么**：隔离测试的 server 虽然 `JIANPU_DB` 指向副本，但 `refresh.sh` 的输出目录
`data/` 走的是 **`HERE_WEB`（真机 `jianpu-web/data`）**，skill 同步也写向真机 `jianpu2/skills/…`。
于是 02:31 那一轮把副本的解析结果写进了**线上索引与 skill 副本**，线上多出 1 首测试曲
`测试投稿曲`（`来源 'user': 1`）。

**怎么发现的**：清理时对比三处曲数：真机 `data.jsonl` 7321、skill 副本 7322、线上 `stats.json`
7322，且 `grep 测试投稿曲 songs.jsonl` 命中 1 —— 三处不一致就是证据。

**怎么复原的**（都是可重生成的产物，语料本身没动）：

```bash
python3 jianpu-web/tools/build_web_data.py --data jianpu-db/data.jsonl --out jianpu-web/data   # 线上索引
cp jianpu-db/data.jsonl jianpu2/skills/jianpu-melody-lookup/data.jsonl                          # skill 副本
```

复原后：**7321 首 / 1,301,430 音高音 / 336,414 小节不变**，`grep 测试投稿曲` 0 命中，
`jianpu-db` 的 `data.jsonl`/`data.json` 全程逐字节未变（`git status` 只有我改的代码）。
**教训**：隔离测试必须连 `jianpu-web` 一起抄（现在 `check_submit.py --live` 的 docstring 里写明了
"请指向隔离实例"）。这条已写进 §5 的自检清单。

> 三个"音符数"别混（都是对的，口径不同，以后引用请带口径）：
> * **1,301,430** = 音高音（含 `#b` 记号、不含休止）—— `stats.json` 与网页上显示的就是这个；
> * **1,429,986** = `data.jsonl` 的 `n_notes` 字段 = 音高音 + **128,556 个 `0`休止**；
> * 336,414 = 小节数（`bars` 合计，休止**按拍计入**小节，见 jptok 的定案）。

## 5. 顺手清掉的 32MB 调试垃圾（对语料零影响）

`scores/` 里躺着 **7,820 份 `*_expand.txt`**（`score.py:write_expand()` 的调试产物，32MB）。
`parse_scores.py` 本来就跳过它们，**但**：

* `jianpu2/tools/melody_oct.py`、`famous2.py`、`todo_names.py`、`misc/records/probe_h_*.py`
  只 `glob scores/*.txt` 而**不过滤** → 这些工具一直在把 7,820 份副本当曲谱统计；
* `ls scores/*.txt | wc -l` 数出的不是真实曲数（15640 vs 7820），以后做体检会被误导。

处理：`git rm` 掉 7820 份 + 写进 `.gitignore`（文件仍在 git 历史里，`write_expand()` 也能重生成）。
**安全性证明**：删前/删后各跑一次 `parse_scores.py`，`data.jsonl`/`data.json` **逐字节一致**。
提交：`jianpu-db 7e46a02d`。

**后来又抓到根因**：删完我跑了一次 `export_hf.py`，7820 份**又全回来了** —— 因为
`score.py:parse()` 里**无条件**调 `self.write_expand()`，而 `parse_scores.py` /
`export_hf.py` 每首歌都会走 `parse()`。也就是说：**每次 refresh（补一次链接/标签就会触发）
都在重造 32MB 调试副本**，这也解释了它们当初怎么被提交进仓库的。
已改成默认不写（`JIANPU_WRITE_EXPAND=1` 或显式调 `write_expand()` 才写，提交 `jianpu-db b72b73ca`）。
验证：`parse_scores.py` 连跑两次、`export_hf.py` 再跑一次 → `_expand` 数量始终 0，
`data.jsonl` 逐字节不变，`scores/` 从 142M 回到 **87M**。
