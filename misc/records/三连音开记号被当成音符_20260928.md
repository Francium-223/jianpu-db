# 三连音开记号 `3[` 被当成了音符 —— 用户当场纠正的一个真 bug

日期: 2026-09-28（用户指出）
涉及: `jianpu2/skills/jianpu-melody-lookup/jptok.py`（唯一口径）、`jianpu-db/score.py`（兜底口径）、
`jianpu-db.github.io/static/jptok.js`（前端口径）、`jianpu-db.github.io/tools/build_web_data.py`（站点构筑兜底）

## 用户的原话

> 你看好了，`3[ 5 3 4 ]` 这里的 `3[` 和 `]` **都不算有效音符**的！！！那是**三连音**！！！

对，是 bug。jianpu-ly 里三连音写作 `3[ … ]`：那个 **`3` 是连音数**（3 个音占 2 个音的时值），
`[` / `]` 是**分组记号** —— 三个字符都不该算成音符。

## 根因

`jptok.py` 的白名单正则末尾写着 `(?P<mark>[\[\]]?)$` —— **允许 token 以 `[` 结尾**。于是：

```
parse_token('3[')        -> (3, 0, 0)          # 记号被当成音级 3
seq('3[ 5 3 4 ]')        -> [3, 5, 3, 4]       # 4 个音，凭空多出一个 3
```

而 `]` 单独成 token 时本来就不匹配（没有音级），所以只错在开记号这一侧。

## 实测影响面

| 位置 | 数 |
|---|---|
| 语料 `data.jsonl` 里的 `<时值>3[` | **66** 处（`q3[` 44 / `3[` 13 / `s3[` 7 / `c3[` 2） |
| 受影响曲目 | 4 首: `th06_15` 40 / `qd1z_anthem` 13 / `th10_06` 11 / `th075_34` 2 |
| 手抄 GT（`train-work/gt/*.txt`） | `3[` 23 处 + `]` 23 处（全在 `Lemon_用户.txt`） |

修前/修后**音符数**（同一份谱，只换口径）：

```
qd1z_anthem.txt   245 -> 232   (-13)
th06_15.txt       362 -> 322   (-40)
th075_34.txt      216 -> 214   ( -2)
th10_06.txt       423 -> 412   (-11)
```

**自检门自己也在保护这个 bug**：用例①写着"th10_06 音符数 = 415"，而 415 正好是**把 11 个 `3[`
也算成音**之后的数 —— 真值是 **404**。另外两条"无音符被静默丢弃（数字数==旋律数）"的不变量
在那 4 首上误报（naive 数字扫描把 `3[` 里的 3 也数了进去）。三处期望值都已按真值改写。

还有一件值得记的事：仓库里**本来就有**一个专门查这个的工具 `tools/survey_notation.py`
（docstring: "看 GT/曲谱里三连音标记、连音线、圆滑线到底怎么写的 —— **决定解析规则**"），
它一直在报 `3[` 这种 token，但那个结论**从来没落到白名单里**。教训：调查工具的输出要变成断言/规则，否则等于没查。

## 修法（四处口径一起改，否则就是第五次"口径分叉"）

1. `jptok.py`（唯一真源）: `(?P<mark>[\[\]]?)$` → `(?P<mark>\]?)$`，并把这段经历写进 docstring。
2. `jianpu-db/score.py` 的内置兜底: 同样改 `mark` 组（CI/独立 clone 走这条路）。
3. `jianpu-db.github.io/static/jptok.js`: 同样改，并重建 dist（`jptok.f2563838.js`）后同步到仓库根。
4. `jianpu-db.github.io/tools/build_web_data.py` 的兜底正则: 同样改（站点的"音符数"徽章走它）。

**验证**（全部本机实测）:

## 连音组内部的时值压缩 —— 当天也补上了

第一版只做到"`3[` 不算音符"，组内三个音按各自**字面**时值计时，于是含连音的 4 首**小节线会偏**。
随后把缩放也实现了，算法**抄参考实现**（`jianpulocal/mxml2jp-main/jianpu-ly_patched.py:1786`）：

```python
fitIn = int(word[:-1])                      # '3[' -> 3
i = 2; while i < fitIn: i *= 2              # i = 4
num = int(fitIn*3/2) if i == fitIn else int(i/2)   # 4 != 3 -> num = int(4/2) = 2
notehead_markup.tuplet = (num, fitIn)       # 时值 × num/fitIn = 2/3
```

证据链（都不是推理）：参考实现的语法说明写着 `Tuplets: 3[ q1 q1 q1 ]`；
它渲染出来的 `train-work/gt/Lemon_用户.ly` 里那个连音组正是
`\times 2/3 { … \note-mod "7" b8 … \note-mod "7" b8 … }` —— 八分音符 × 2/3 = 1/3 拍。
组内个数 = `fitIn`，遇 `]` 收组，或装满自动收（语料里 MIDI 转来的 40 处**没有** `]`）。

实测：`tuplet_ratio` 与参考同式（`3[`→(2,3) / `5[`→(4,5) / `6[`→(4,6) / `8[`→(12,8)）；
GT 例句 `4 - '1 3[ q7 ~ q7 '1q ] 5 - 4` 的 bars = `[5, 9]`，与手算一致；
与 `score.py` 兜底逐首比 `recover_bars`（204 首，含 4 首连音）**不一致 0 首**；
自检门用例⑤（th10_06 第一条线在第 3 个音之前）仍通过。
