# 工具链烂了两个口子：冒烟清单是手写的（2026-09-25 夜）

## 怎么撞上的

这一轮想把「金曲缺口」里还没爬到的 25 首补回来，于是去用 `tools/crawl_jianpucn_by_title.py`
（按曲名扫 jianpu.cn 的字数分类目录，只下命中的那几张）。一跑就崩：

```
FileNotFoundError: [Errno 2] No such file or directory: 'D:\\Documents_D\\jianpu2'
```

它的第 21 行硬编码着**作者 Windows 机器的 `os.chdir`**，在 Linux 上必崩。
而 `scripts/check_tools.sh` 全绿 —— 因为这个文件**不在冒烟清单里**。

## 两个口子的共同根因

`check_tools.sh` 的 `TOOLS` 是**手写清单**，而不是扫 `tools/*.py`：

```bash
TOOLS="add_link propose_tags ... fix_residual_titles"
for t in $TOOLS; do
  [ -f "tools/$t.py" ] || continue        # ← 文件没了就**静默跳过**
  python3 "tools/$t.py" --help
done
```

于是：

1. **清单里有、文件却没有**：`batch_pipeline`、`make_score`、`mbz_lookup` 三个早就没了
   （`mbz_lookup` 应已改名成 `mbid_lookup`），`|| continue` 让它们静默消失 ——
   清单看着覆盖了，其实没有。
2. **文件有、清单里却没有**：`crawl_jianpucn_by_title.py` 就这么烂着没人知道。
   顺手一查，`detect_sections`、`tlsfetch`、`propose_title_cleanup` 也都不在清单里。

`tools/` 下现在有 **582 个 .py**，绝大多数是一次性的 `_*`/`diag_*`/`qa_*` 试验脚本，
不可能全进冒烟 —— 所以清单本身是合理的，**问题是清单能悄悄漂移**。

## 改了什么

1. **`crawl_jianpucn_by_title.py` 修好**：
   * 删掉硬编码的 `os.chdir(D:\...)`，改成按 `__file__` 定位 `ROOT`/`WS`（与别的工具同口径）；
   * 输出改为工作区图库 `JIANPU_IMAGES` 或 `<工作区>/images-prep/jianpucn-title`（不再靠 cwd 对上）；
   * 扫描日志 `train-work/jianpucn_title_scan.tsv` 也改成绝对路径；
   * **加 `--help` 保护** —— 它是模块级脚本，不拦的话 `--help` 会被当成"要爬的曲名"，
     真的开始扫几万页目录；
   * 取页统一走 `tlsfetch`。

2. **冒烟清单不再允许静默漂移**：清单里有、`tools/<名>.py` 不存在的，**明确算失败**
   （不再是 `|| continue`）。同时删掉 `batch_pipeline`，把 `mbz_lookup` 换成真实存在的 `mbid_lookup`，
   并补进 `crawl_jianpucn_by_title`、`detect_sections`、`tlsfetch`、`propose_title_cleanup`。

3. **`mbid_lookup.py` 加 `--help` 保护**（顺手抓到的同类隐患）：
   它没有 argparse，而 `--help` 会被当成**曲名**，真的去打一次 MusicBrainz ——
   实测返回的是 Harry Potter 那一堆，退出码还是 0，所以"看着 OK"。
   （我第一遍就是这么被骗过去的：只看了退出码。）加保护后 `strace` 确认 `--help` **0 次网络调用**。

那 25 首里 23 首用修好的按曲名爬虫去扫 jianpu.cn（`落` 和 `The Beast` 扫不到 ——
该工具"按字数挑分类"的表只映射 2–9 字，1 字与 0 字都掉进"十字以上"分类）。

### 5.3 坑一：下载阶段**静默失败**（报"下载 0 个谱页"，退出码 0）

第一次跑完，扫描明明命中 12 页，下载却报 0，而且**没有任何错误**——因为下载循环里是

```python
try:  ph = get(...)
except Exception: continue      # ← 出错就悄悄跳过
```

我是靠事后手工复现（同一个 URL 明明能下）才确认不是站点问题。**改了**：

* 失败原因计数并打印（`页面取不到: XxxError` / `页面里没匹配到 /img/ 谱图` / `图片下载失败: XxxError`）；
* 加 `--from-log`：直接读扫描日志里已命中的谱页去下载，**不再重扫目录**
  （扫 6 个分类要 ~40 分钟，而"扫描"和"下载"本来是两件事）。

加上 `--from-log` 重跑，12 页全部下载成功。
**原始失败的确切原因没法回溯确认了**（异常被吞掉了）——这正是把失败原因打出来的理由。

### 5.4 坑二：目录名里的 `&nbsp;` 一路漏进语料

下载下来的目录名是 `阿姐鼓&nbsp;&nbsp;__jianpucn-123733` —— 站点标题里的实体没清。
`queue_from_crawl.py` 把目录名解析成转写队列的**"曲名"列**，于是转写完就会变成
`title=阿姐鼓&nbsp;&nbsp;`：**实体漏进语料**。

* 爬虫的 `safe()` 已加 `ENT.sub("", s)`（以后不会再有）；
* 新增 `tools/fix_image_dir_entities.py`（`--plan`/`--apply`），把**已经下下来的**目录改名：
  **239 个目录**（jianpucn-title 209 + test-jianpucn 30），改名后全库实体目录 **239 → 0**；
* 重新生成队列：含 `&nbsp;` 的队列行 **109 → 0**；5 首缺口歌现在都在队列里（各 1 条）。
