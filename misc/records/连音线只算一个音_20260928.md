# 连音线 `~` 只算一个音 —— 用户口径落地（顺带把指标抬上去了）

日期: 2026-09-28（用户指出：「还有 `~` 要看作一个音符」）
涉及: `jptok.py`（唯一口径）、`lookup.py`、`jianpu-db/score.py`（兜底）、`站点 tools/build_web_data.py`、
`selfcheck`（不变量）、`tools/eval_gt.py`

## 用户口径

> 还有 `~` 要看作一个音符。

对，`~` 是**连音线**：同一个音被唱/奏长一些，记谱上写成两个音头 + 一条弧线，人只数成**一个音**。
（`~` 这个记号本身从来不是音符 —— 这一点原本就是对的；错的是**两个音头被数成了两个音**。）

## 修前的实测影响面

| 位置 | 数 |
|---|---|
| 语料里含 `~` 的歌 | **3,079 首** |
| `~` 记号总数 | **14,661** |
| ├ 两侧音级+变音完全相同（铁定是连音线） | 13,207 |
| ├ 只差八度记号（转写把八度标歪了的连音线） | 1,452 |
| └ 音级不同（**圆滑线**，不该并） | **2** |
| 手抄 GT 里的 `~` | 84（同音 80 / 异音 4） |

口径定案：**并的判据 = 音级 + 变音相同（不看八度）** —— 检索口径本来就不看八度；只有那 2 个真圆滑线保持两个音。

## 修法与验证

* `jptok.pitched(score, merge_ties=True)` 成为**唯一**音高序列口径；`seq()` 是它的别名（默认并）。
* `lookup.pitch_and_oct()`（检索索引）、`score.py` 的兜底 `seq()`、站点 `build_web_data.py` 的音高串
  全部改成同一份逻辑 —— 它们原来各自循环调 `parse_token`，是"第五份口径"的隐患
  （自检门的不变量 ④b 当场抓出 3058 首不一致）。
* `recover_bars()` 里"第几个音符"的计数也要跟着并，否则**小节线/高亮会整体错位**（3058 首）。
* `selfcheck.digits_of()`（naive 数字扫描）同样跳过连音线的第二个音头，否则 ④/④b 误报。

**并 `-` 的边界**：`'1 - ~ '1` 这种写法（note + 延长 + 连音线 + note）里，`-` 是**延长**，
不该打断连音线。第一版把 `-` 当"非音符记号"从而打断了它，导致**语料比站点多 6 个音**
（3 首：`qd1z_anthem` / `th01_10` / `th01_06`）。改成"`-` 不打断连音线，休止/念白才打断"后两边**逐首一致**。

```
语料: 并后 1,596,512 音   ·   音头数(不并) 1,610,973   ·   被并掉 14,461
站点 stats.notes = 1,596,512（与语料**逐首**一致, 不再差 6）
自检门 9 条全 OK · jptok<->兜底 762 万 token 逐项一致 · 站点 5 组自检全过 · bars 越界 0 首
```
