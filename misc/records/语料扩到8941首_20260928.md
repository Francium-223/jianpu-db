这一轮不是新转写, 而是**把已经转写完、却一直躺在成品目录里的谱导入语料** —— 不需要 GPU,
一次 +22.2%。

---

## ① 怎么发现的

对账两个目录:

```
jianpu-db-out/scores  8573 份   <- 成品(已转成 jianpu-db 格式)
jianpu-db/scores      7816 份   <- 语料目录
→ 在成品里、不在语料里的: **1639 份, status 全部是 ocr**(白名单内的!)
```

流水线是**两段式**: `batch-out/`(裸 token) --`to_jianpu_db.py`--> `jianpu-db-out/scores/`
--> `jianpu-db/scores/` --> `parse_scores.py` --> `data.jsonl`。

**中间那一步(成品 -> 语料目录)原先没有通用工具**: `kugou_pipeline.import_to_db()` 只管酷狗那一批,
`batch_transcribe_queue.py --stage import` 要队列文件。而 `tools/coverage_report.py` 里的口径表
**直接把成品目录标成"② + `jianpu-db-out/scores`(待入库)"** —— 所以这些谱按设计就是**等着入库**的,
不是被剔除的。每轮 `finalize` 会轮换重建成品目录(07:16 那次 `scores` -> `scores-prev`),
新谱就留在那儿等下一步。

## ② 判据与做法(全部复用流水线自己的口径, 不另立一套)

新增 `jianpu2/tools/import_finished_scores.py`:

* **只拷不覆盖** —— 目标已有就跳过(语料里那份可能已被人工修过, 绝不能拿成品盖回去);
* **只拷不删** —— 不移动、不删除任何文件;默认 **dry-run**, 要 `--apply` 才写;
* 跳过判据:
  * `status` 不在 {ok, ocr};
  * **旋律音 < 5** —— 检索下限就是 5, 这种谱永远查不到(`quarantine_short_scores.py` 的判据);
  * **念白异常**: token >= 20 且 x >= 10 且 x 占比 >= 0.30(`quarantine_highx.py` 的判据, 全库 x 占比 3.4%)。

dry-run 结果:

```
成品 8573 份 -> 目标已有 6934 / 旋律音<5 共 16 / **可导入 1623**
```
