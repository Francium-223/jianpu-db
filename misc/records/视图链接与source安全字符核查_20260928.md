"单个安全 token"是这个字段的不变量, 现在 8905 份全部合格。

## 假警报 ①:`os.path.exists()` 判相对符号链接,**100% 报悬空**

第一版检查写的是:

```python
if os.path.islink(p) and not os.path.exists(p):   # <- 错
    dangling.append(...)
```

结果:`符号链接共 52926 个, 目标缺失 52926 个` —— **100%**。这个比例本身就是"尺子坏了"的信号。
拿一个具体链接验证:

```
os.readlink(p)   = ../../scores/th16_01.txt
os.path.realpath = D:\Documents_D\jianpu-db\scores\th16_01.txt   (存在 ✓)
os.path.exists(p) = False                                        (✗ 假)
PowerShell Test-Path -LiteralPath <链接> = True                   (✓)
```

**这台 Windows 上, `os.path.exists()` 对"相对目标"的符号链接会返回 False**, 而 `realpath` 正常。
判是否是悬空链接, 请用 `os.path.exists(os.path.realpath(p))`(或 PowerShell 的 `Test-Path`)。

## 假警报 ②:拿 by_title 的文件名去和 `scores/` 的文件名比, 报 14 处"对不上"

视图目录名/文件名用的是**清洗后的标题**(`score.py` 里对 `?` 等字符做过替换),
**不是** `scores/` 里的原始文件名 —— 所以"名字集合成员"这个测法本身就是错的。
正确的不变量只有一个: **链接能不能解析到真实存在的谱**(见上, 52926 个全好)。

## 假警报 ③:站点索引里 source 字段叫 `s`, 不是 `source`

查"每谱一页"覆盖时, 我按 `s.get("source")` 读站点索引 —— 结果**8943 首全部"没有 source"**,
差点又写出一条"覆盖为零"的结论。实际索引是**紧凑键**(第一条的字段:
`a alias artist bars bpb file g hot id links mbid n o p raw s sc src srcurl st t tags transcriber trunc usertags`),
出处字段是 **`s`**。用对键之后:

```
站点 8943 首, 没有挂上原图的 42 首 —— 全部有解释:
  ① 没有 source=(手工录入的东方曲/校歌那批, 本来就没记出处)   38
  ② source 是兜底值(unknown×2 / 21qupu / qpcxw)              4
  ③ **有 source 但图索引里没有 = 0**  <- 没有静默缺口
```

> 教训与之前几次一样: **先怀疑尺子**。特别是"100% 全坏"或"整齐的差 N"这种结果 ——
> 它们几乎总是口径/API 语义的问题, 而不是数据真的全坏了。

## 顺带:图库里有两类"不干净", 但**都不影响站点**

查"每谱一页"时顺手按**魔数**(不信任扩展名)扫了一遍 38,710 个图片文件:

```
扩展名与真实格式不符: 8642 个(22%)
   .jpg 里其实是 gif : 6127      .jpg 里其实是 png : 2043
   .jpg 里其实是 bmp : 2         .png 里其实是 jpg : 2      .gif 里其实是 png : 2
根本不是图的: 466 个
   MIDI(MThd) 152 / MP3(ID3) 198 / PDF(%PDF-) 123 / 空文件(0 字节) 若干
   —— 爬虫把 midi/mp3/pdf 存成了 .jpg
```

**影响面(实测)**:

* 图索引里**非图文件 0 个**、**第一页是破图的 source 0 个** —— `build_image_index.py` 用 PIL 校验过,
  那些 MIDI/MP3/PDF **根本没进索引**(拿 `jianpucn-69365` 逐个验证过:目录里有那个 MIDI, 索引里没有这个 source)。
  所以**站点上不会有破图** ✓。
* 8,642 个"扩展名撒谎"的文件内容是**合法图片** ✓(GIF/PNG 而名字是 .jpg), 浏览器按内容嗅探照常渲染 ✓;
  唯一不准确的是**本机开发服务器**按扩展名发 `Content-Type`(小改进点, 不影响功能)。

**结论**: 两件都不需要动数据 —— 466 个垃圾文件躺在图库目录里(没进索引, 也没被使用),
扩展名不符的那批是"名字难看但内容没问题"。记在这里, 免得下次又被同一个数字吓一跳。
