# 🧧 锦囊 —— 简谱语料抢救包

> **先读这一页。** 这个 U 盘里是「把简谱图片变成规范简谱文本语料」这件事的**全部家当**：
> 代码、语料、原始扫描件、自训练模型适配器、git 历史。
> 换一台电脑，照下面的「五分钟上手」就能跑起来；要重建整套流水线，看「完整重建」。

## 0. 这是什么（一句话）

一个**中文简谱旋律语料库 + 从图片自动转写它的流水线**：

```
简谱网站  ──爬虫──▶  扫描图  ──视觉模型(OCR/微调)──▶  规范简谱文本  ──▶  语料库 jianpu-db
 (jianpu.cn                                                                    │
  jianpujia.com                                                       ┌───────┴────────┐
  qupu123.com)                                                  旋律查歌(哼一句找歌)   导出 HuggingFace
```

已经做成的成品：**7385 首**带标签/出处/小节线的简谱旋律语料（`data.jsonl`），
以及一个**哼一段旋律就能查出是哪首歌**的检索器（含前端）。

实测指标（见 §5）——**酷狗 2025 华流 Top100 里 61.2% 能在库中定位到；11 个音哼准 Top-1 命中 93.3%**。

## 1. U 盘里有什么 / 怎么解开

全部是 **tar / tar.gz 归档**（不是散文件——这块 U 盘顺序写只有 **5.4 MB/s**，散文件更慢十倍）。
共约 **10 GB**，校验和在同目录 `_manifest.txt`（`certutil -hashfile <文件> SHA256`）。

**解开方法**（Windows 10 以上自带 `tar`；7-Zip 22+ 也行）：

| 归档 | 内容 | 解开命令 | 解出来是 |

## 2. 五分钟上手（只想「哼一句查歌」）

需要 **Python 3.13**（3.10+ 应该也行）和 **numpy**。**不需要 GPU、不需要联网。**

```bash
# 1) 解出语料
tar -xzf 01_jianpu-db_语料.tar.gz
tar -xzf 02_jianpu2_代码与文本.tar.gz

# 2) 进技能目录
cd jianpu2/skills/jianpu-melody-lookup

# 3) 查 —— 输入简谱唱名数字（只认 1-7，# 升 b 降；至少 5 个音）
py -3.13 lookup_acc.py 63731232          # 升号感知版（推荐）
py -3.13 lookup.py 51223323323531        # 老版：纯音级 + 八度
py -3.13 lookup_acc.py "3 3 5 6 5 6 5 3 2"   # 带空格也行
```

输出按「错音数」排序，`0 = 完全一致`。**认谱不清不要紧**：8~15 个音、错 1 个音，
Top-3 仍能覆盖 90%+（§5）。

### 想开网页版

```bash
cd jianpu-web
py -3.13 app/server.py            # 默认 http://127.0.0.1:8770/
py -3.13 app/server.py 9000       # 换端口
```
网页里可以：全文/旋律检索、**把命中的那首原谱摊开并把匹配的音逐个高亮**（像编辑器里搜索那样）、
列出全部元数据、以及**零登录投稿**（纠正/补谱，落在 `feedback/`，会自动 commit）。
设 `JPSUBMIT_TOKEN=xxx` 可要求投稿带口令；不设则是开放投稿（仅绑定 127.0.0.1）。

## 3. 四个目录分别在干什么

### `jianpu-db/` —— 语料本体（**最重要**）

| 文件 | 作用 |
|---|---|
| `scores/*.txt` | 一首一个文件，**jianpu-ly 语法**（含 `title=` `tag=` `MBID=` `alias=` `transcriber=` + `%--` + 段落 `NextScore`） |
| `data.jsonl` | **成品**：7385 首，14 个字段，每首带 `score`（音符串）、`bars`（小节线位置）、`beats_per_bar`、`source`、`MBID`、`tag`… |
| `data.json` | 全量（含未校对状态），用于逐首校对 |
| `tags.json` | **标签体系的单一真源**（DAG + `imply` 蕴涵 + `equal` 别名）；`tag`/`tagroute` 由它推导 |
| `score.py` | `Score` 类：解析曲谱、生成 `by_*` 符号链接索引 |
| `parse_scores.py` | **重建一切**：`py -3.13 parse_scores.py` → 重新生成 `data.json` / `by_*` 索引 / 展开 `R{}A{}` |
| `export_hf.py`、`publish_hf.py` | 导出/上传 HuggingFace（`HF_TOKEN` 环境变量） |
| `melody_find.py`、`semitone_offset.py` | 按数字查旋律 / 转调 |
| `.github/workflows/` | CI：push 后自动重建索引；publish 后自动传 HF |

**状态字段**（`status=`）：`ok` 人工校对 / `midi` MIDI 转换 / `ocr` 图片转写。
`data.jsonl` 只收 `ok` + `ocr` 且音符非空的（白名单，不是"排除 midi"）。

> ⚠️ `by_*` 是**符号链接**索引，exFAT 存不了，包里**没有**。重建命令：
> `cd jianpu-db && py -3.13 parse_scores.py`（会把 2 万多个链接重新建好）。

### `jianpu2/` —— 转写流水线 + 技能

| 入口 | 作用 |
|---|---|
| `crawler.py` | 爬虫：jianpu.cn / jianpujia.com，按分类或关键词，断点续爬；每首存 `<歌名>__<站点>-<id>/001.jpg` + `song.json` |
| `convert.py` | 转写：图片 → 规范简谱文本（本地 Ollama 视觉模型；含大量自动规范化规则） |
| `tools/preprocess.ps1` | 图片缩放 + 切横条（小模型必需） |
| `tools/*.py` | 批处理：后处理、校验、补 MBID、爬取状态、重建索引… |
| `skills/jianpu-melody-lookup/` | **旋律查歌技能**（本包最有用的东西，见下） |
| `vendor/jianpu_ly/` | 内置 jianpu-ly，免安装 |
| `train-data-*`、`train-work/` | 微调数据集（`.jsonl`）与工具脚本、评估集 |
| `models/` | 自训练 LoRA 适配器（已单独打包） |

**`skills/jianpu-melody-lookup/` 里有什么**

| 文件 | 作用 |
|---|---|
| `jptok.py` | **唯一**的简谱 token 解析器（音高/升降/八度/时值/小节线恢复）。**所有脚本只许用它** |
| `lookup_acc.py` | 升降号感知检索（发送从严、接收从宽：输 `5` 能中 `#5`，输 `#5` 更精确） |
| `lookup.py` / `lookup_norm.py` / `lookup_exact.py` | 纯音级 / 归一化 / 精确子串三种口径 |
| `eval_golden.py` | 金曲清单指标（§5 那张表就是它跑的） |
| `eval_metric.py` | 随机留一口径（模拟"没有原谱、纯凭记忆"） |
| `gate.py` + `selfcheck/` | **自检门**：已知答案用例不过就不出结果（见 §7 坑 2） |
| `show_hit.py` / `check_hit.py` | 把库里命中那一段原样摊开（带记号） |
| `show_song.py` / `find_in_song.py` | 按**小节**打印整首谱 / 在单首谱内找最接近的窗口 |
| `SKILL.md` | 技能说明书（给 AI 助手看的前言 + 用法） |

### `jianpu-web/` —— 查歌前端

`app/server.py`（标准库 http.server，无框架、无构建）+ `static/`（原生 ES module）+ `data/songs.jsonl.gz`。
检索在前端本地做（滑动窗口 + 非对称代价），所以**打开就快、不依赖后端**。
`tools/check_*.mjs` 是页面/检索/高亮的自检脚本。
**每一首谱还有自己的页面 `/s/<id>`**（2026-09-24 加，用户要求"像 abcnotation 那样显示原图"）：
左边是抓取到的**扫描件原图**（`/img/<相对工作区的路径>`，由 `app/server.py` 发；8.9GB 的图不进 git），
右边是全部元数据 + 收录页 + 补标签，下面是带小节线的原文。原图索引 `data/images.jsonl.gz` 由
`tools/build_image_index.py` 按图片目录名 `…__<source>` 扫出来（**7,281/7,321 首有图，共 9,073 页**）。

### `jianpulocal/` —— 东方侧工具与数据

| 文件 | 作用 |
|---|---|
| `scores/` `new/` | 早期曲谱与中间产物 |
| `touhouSTG.py`、`tmidi.py`、`mxml2jp.py` | MIDI/MusicXML → 简谱；东方曲目解析 |
| `parse_tags.py`、`tag_implications.json`、`tag_equality.json` | 标签体系的早期来源（新版已并入 jianpu-db/`tags.json`） |
| `mbid_*.py`、`resolve_by_release.py` | 用 MusicBrainz 给曲目补 MBID |
| ~~`touhou-midi-collection/`~~ | **2.1 GB 东方 MIDI 集，没打进包**（可重下，见 §6） |

## 4. 完整重建（从零把这套东西跑起来）

```bash
# 0) 依赖
py -3.13 -m pip install numpy            # 检索/评测要
#  转写还要: 本地 Ollama + 一个视觉模型
#     ollama pull qwen2.5vl:7b            # 整图转写用这个
#  可选: LilyPond(渲染 .ly 预览)、py -3.13 -m pip install jianpu-ly(vendor 里已内置)

# 1) 语料侧（jianpu-db）
cd jianpu-db
py -3.13 parse_scores.py                 # 重建 data.json / by_* 索引 / _expand.txt

# 2) 转写侧（jianpu2）—— 抓新图并转写
cd ../jianpu2
py -3.13 crawler.py jianpucn --cat sanzigepu --pages 3 --out images/jianpucn
powershell -ExecutionPolicy Bypass -File tools/preprocess.ps1 -Source images/jianpucn -Dest images-prep/jianpucn -Strips 240
py -3.13 convert.py --input images-prep/jianpucn --out scores-out --model qwen2.5vl:7b --transcriber 你的ID --tags 华语

# 3) 并入语料
cp scores-out/*.txt ../jianpu-db/scores/
cd ../jianpu-db && py -3.13 parse_scores.py
```

要**微调自己的识别模型**：`jianpu2/train-work/` 里有数据集与训练脚本；
`06_模型_adapters.tar` 里的 LoRA 可直接挂到对应基座上（§6 有基座型号）。

## 7. 踩过的坑（**照着躲，别重犯**）

1. **口径必须只有一份。** 简谱 token 的解析原来在 5 个地方各写了一份正则，
   结果白名单不一致，**全库带 `#` 的音整段从 `data.jsonl` 里消失**（18 首受影响），
   检索永远匹配不上，查了三轮才定位。现在只有 `jptok.py` 一份，**谁也不许再写第二份**。
2. **改完必须自检，不许"改完就宣布完成"。** 曾经有个解析器把 231 个音符读成 377 个，
   **凭空造出"完全一致"的假命中**。现在所有检索/评测脚本开头都跑 `gate.gate()`：
   `th10_06` 音符数必须是 231、`63731232` 必须 0 错命中、`33565653253` **不许**有 0 错命中；
   不过就 `exit 3`，一个数字都不出。
3. **`to_record()` 里有硬编码字段白名单。** 加新字段忘了加进去 → 字段静默丢失。
   加字段后**必须**回读 `data.jsonl` 验证。
4. **写语料时别的进程还在写 = 索引与磁盘不一致。** 有僵尸进程 + 定时任务并发写，
   出现过 `OSError [WinError 145]`。改完先 `rebuild_when_idle.py`（等写手停 → 重建 → 校验）。
5. **exFAT 没有符号链接**，`by_*` 必须重建（§3）。
6. **检索里"八度"不参与打分**（按用户口径：一般人标升降的概率远高于标八度）。
   八度只作为并列时的展示列。
7. **升降号是"非对称代价"**：库里 `#5` 能被输入 `5` 命中（代价 1），
   但输入 `#5` 命中库里的自然 `5` 要罚 2、命中 `b5` 罚 3 —— **发送从严、接收从宽**。
8. **`eval` 类脚本别用"整行归一化"处理榜单**：3 列 TSV 要把 `歌名/歌手` 与 `片段` 分开取，
   否则 `"2晴天周杰伦"` 这种整行会被当成查询，指标直接掉到 7/98。

# 🚑 补遗十（2026-09-25 凌晨，GitHub Actions 一直被一个**假 submodule** 卡住）

用户："现在GH那边还报错呢" —— 报在 `actions/checkout` 阶段：
`fatal: No url found for submodule path 'jianpu2' in .gitmodules`。

**根因是 CI 自己造出来的**：`jianpu-db` 树里有一条 `160000 commit b7c7826a… jianpu2`（gitlink，即子模块记录），
但没有 `.gitmodules`。它是 bot 提交 **`2f60fb58`** 加的，而那条提交**只改了这一个条目**（`data.jsonl` 没变）：
`parse.yaml` 先把兄弟仓库 checkout 到**仓库内**的 `jianpu2/`，紧接着 Commit 步骤的 `git add -A`
就把它当 submodule 记了进去。之后**每次**带 `submodules: recursive` 的运行都必挂，
而错误出现在 checkout 阶段、跟当次改动毫无关系 —— 极难查。

修法（`51af08ff`）：`git rm --cached jianpu2`（那个目录本来就是空的）；`.gitignore` 加 `jianpu2/`；
`parse.yaml` 的 Commit 步骤加"索引里出现 160000 就直接 `::error::` 失败"的兜底（并显式 `shell: bash`，
因为该 job 默认是 pwsh）。顺手注明：sibling checkout 其实**落错了地方**（`score.py` 找的是
`<repo>/../jianpu2`，checkout 落在 `<repo>/jianpu2`），所以 CI 一直走的是兜底 jptok 口径。
修完的验证要**逐条读 run 页面的 Status**（徽章只反映"最近一次已完成"，会骗人）：
`#45 9166a4e Failure`（修前）→ `#46 51af08f Cancelled`（我两次推送挨太近被 concurrency 取消）→
`#47 4a6828b Success` → `#48 e167de0 Success`；两个 workflow 徽章也都 passing；
且没有再产生 bot 提交（远端 `data.jsonl` 与本地 md5 一致 —— 顺带复验了"兜底 jptok 与唯一实现等价"）。
记录：`_analysis/GitHub_CI_假submodule_2026-09-25.md`（已镜像进 `jianpu-db/misc/records/`）。
