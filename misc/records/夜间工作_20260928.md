## 一、最要紧的两件事：Windows 上 `parse()` 会改脏语料和索引

自检工具 `tools/check_sideeffects.py` 报 **B 项失败**：
"解析语料内的一份谱后 git status 没变（规范化是幂等的）"。查下去，**两个 bug 同一个根因**：

**根因**：`scores/x.txt` 在 Windows 上传进 `Score()` 时是**反斜杠**（`scores\x.txt`），
而 `score.py` 里到处用 `self.score.split('/')[-1]` 取文件名 —— 按 `/` 切不开。

| # | 症状 | 后果 |
|---|---|---|
| 1 | `write_buf()` 把首行写成 `%scores\x.txt`（应为 `%x.txt`） | 每跑一次 parse 就往曲谱首行**加一行垃圾**，非幂等 → 语料被反复改脏（`th10_06.txt` 就是这样被写脏的） |
| 2 | `make_link()` 拼出 `by_tag/ZUN/scores/x.txt`；pathlib 在 Windows 上把 `\` 也当分隔符 | 在 `by_*` 树里**长出一层叫 `scores` 的目录**，实测 20 个（`by_MBID/<uuid>/scores/`、`by_status/ok/scores/`…），每个带 1 条链接 |

CI 在 Linux 上 `/` 本来就是分隔符，所以这两个 bug **只在 Windows 复现**，一直没被发现 ——
而这台机器就是 Windows。

**修法（一行，零风险）**：`Score.__init__` 里统一 `self.score = score.replace('\\', '/')`
（`open()`/`shutil` 在 Windows 上都接受正斜杠）。

**验证**：
- 清掉 20 个垃圾目录 + `git checkout` 还原被写脏的曲谱 → 全量 `parse_scores.py`（500 秒）→
  **`scores/` 一个字节都没变**（幂等了），垃圾目录也没再生成；
- `check_sideeffects.py` **5 项全绿，退出码 0**（修前是 4 绿 1 红）。

## 四、一个"看着吓人、结论是 0 影响"的调查：和弦 token

`qa_corpus.py` 报了 2 种"格式异常的 token"。顺藤摸下去发现源文件里有 `d,,2,,1`、`,,b3,,2,,1`
这类 token，量很大（226 份谱 / 26.9 万处）。

**先纠正我自己的误判**：这不是"两个音粘一起（空格丢了）"，而是 **jianpu-ly 的和弦写法** ——
`vendor/jianpu_ly/__init__.py:parseNote()` 里
```python
figures = ''.join(re.findall('[01234567x-]', word))   # 一个 word 里所有数字都是同时发声的音
```
所以 `,,2,,1` = 低八度的 2 与 1 齐奏。jptok 是**线性旋律口径**，解析不了和弦 → 整个 token 丢掉。

**按正确口径重新量化**：

| 范围 | 含和弦的谱 | 和弦 token | 里面的音 |
|---|---|---|---|
| `scores/` 全库 | 226 份（**全部 `status=midi`**） | 269,621 | 664,905 |
| **真进 `data.jsonl` 的** | **0 份** | **0** | **0** |

**结论：对发布语料 0 影响**（`data.jsonl` 的白名单只收 `ok`/`ocr`，不收 `midi`）。
但留一条**潜在风险**记在这里：**如果哪天把白名单放宽到收 `midi`，这 226 份会带着"和弦整段消失"
进来** —— 届时需要先定一个和弦口径（例如"取最高音"）。
