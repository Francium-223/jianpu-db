# 整份重转会给成品改名 —— 实测 76 首"转出来了却从没进语料"

日期: 2026-09-28
工具: `tools/check_convert_rename_drift.py`(改名漂移, 只读)、`tools/check_convert_damage.py`(损失量化, 只读)、
`tools/convert_new_batches.py`(增量转换, 修复手段)、`to_jianpu_db.py`(新增 `--outdir/--only/--avoid`)

## 现象

流水线是**两段式**的: 转录只往 `batch-out/` 写**裸 token**; 成品目录 `jianpu-db-out/scores/`
要靠 `to_jianpu_db.py` 把 `batch-out/*.txt` **整份**重新转一遍。今晚查流水线的时候发现
成品目录里 8573 份的 mtime 只有两个时间戳 —— **今天 07:16 / 07:17 两分钟内被整份重写过**
(8569 份), 也就是说"整份重转"是**每晚都在跑**的动作。

问题在于: 成品文件名是**按曲名**定的, 撞名才加 `_2`/`_3`, 而加不加取决于
`sorted(batch-out/*.txt)` 的**遍历顺序**。往 batch-out 里新丢一批谱之后再整份重转,
新谱若排在前面, 就会**占掉**原来的 `X.txt`, 老谱被挤成 `X_2.txt`。

## 实测（不是推理）

`check_convert_rename_drift.py` 把命名过程抄了两遍在内存里对比, 不动磁盘:

| 量 | 数 |
|---|---|
| `batch-out/*.txt` | 9,063 |
| 模拟 A(全部谱) 得到名字 | 8,992 |
| 模拟 B(只算"今天之前就有的"旧谱) 得到名字 | 8,570 |
| **抢走旧名的新谱** | **165 首** |
| **被迫改名的老谱** | **178 首** |
| 其中名字会被新歌**顶掉内容**的现成成品 | 14 份 |

单看"抢名"还不够说明损失, 于是 `check_convert_damage.py` 又查了两件事:
把每首抢名新谱的旋律(音级+时值, 忽略八度)在 `data.jsonl` 里按指纹搜一遍。

| 量 | 数 |
|---|---|
| 抢名新谱里旋律**已在语料中**(别的源转过同一首) | 89 首 |
| 抢名新谱里旋律**不在语料里** = **转出来却从没入库** | **76 首** |
| 老谱被改名后 db 里出现"同名两份、旋律相同"(=重复) | 2 组(`一起走过的日子`、`小螺号`) |

丢失是这么发生的:
1. 整份重转把 `上海滩.txt` 的内容换成了新源的转写, 老源那份改叫 `上海滩_2.txt`;
2. 导入 `import_finished_scores.py` 的口径是**只拷不覆盖** —— `上海滩.txt` 在 db 里已存在,
   于是新转写被**跳过**(丢), `上海滩_2.txt` 不在 db 里, 于是老转写被**又拷一份**(重)。
所以"整份重转"配上"只拷不覆盖"= 新歌丢、老歌重, 是一个**安静的**双向损坏。

## 修复

1. `to_jianpu_db.py` 新增三个开关:
   * `--outdir <目录>`: 落点隔离(先转到空目录里, 不碰现成成品);
   * `--only <名单文件>`: 只转名单里的 batch;
   * `--avoid <已用名目录>`: 先把该目录里已有的输出名占住, 新谱自动退到 `_2`/`_3`(即"躲开"而不是"抢");
   * 另外每跑一次会在落点写 `_converted.tsv`(`batch 名 -> 成品名` 的来源清单)。成品文件里只有
     `%<成品名>`, **原本没有任何来源信息** —— 这也是为什么之前只能整份重转: 光看成品根本不知道
     "某个 batch 到底转过没有"。
2. `tools/convert_new_batches.py`(新): 增量入库的正规做法 —— 账本 `train-work/converted_batches.txt`
   记账"哪些 batch 名转过了"(账本不存在时按 mtime 播种: 早于成品最新 mtime 的算已转过),
   只转账本里没有的, `--avoid` 躲名, 再**只拷不覆盖**地并进成品。`--also <名单>` 用来补转
   "转过但被跳过"的谱(播种时会把这些名字**剔除**, 否则账本一播就把它们永久锁死)。
3. `tools/rebuild_when_idle.py` 新增 `--convert`: 在 `--import` **之前**先跑转换, 于是
   "转录 -> 转换 -> 导入 -> 重建 -> 前端" 这条链终于能一条命令跑完。
4. 丢失的 76 首已写进 `_analysis/lost_batches.txt`, 由 `--also` 喂给转换工具补转。

## 仍然开着的

* db 里那 2 组重复(`一起走过的日子`、`小螺号`)没动 —— 按"只移不删"的口径, 去重要用户点头
  (`audit_corpus_quality.py --apply-dup` 已有能力, 但会让对外数字变小)。
* 今晚之前**每次**整份重转有没有造成同样的丢失, 没有逐次追溯: 只有成品 mtime(07:16)这一个点能查
  —— 好在来源清单 `_converted.tsv` 从今天起会一直记下去, 以后可以精确追溯。
